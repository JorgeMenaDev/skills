# Architecture And Change Choice

Use this reference to decide the durable ownership boundary before choosing tools.

## Inspect First

Read the nearest agent instructions and inventory the repository's apps, packages, lockfile, scripts, Expo/native config, native directories, auth/backend packages, and pinned versions. Commands are discoverable examples, not universal instructions:

```sh
rg --files -g 'AGENTS.md' -g 'package.json' -g '*lock*' -g 'app.json' -g 'app.config.*' -g 'eas.json' -g '*.xcodeproj/**' -g '*.xcworkspace/**'
rg 'expo|react-native|swift|clerk|convex|metro|runtimeVersion' -g package.json -g 'app.config.*' -g app.json -g eas.json
xcodebuild -version
```

Inspect installed package types, the active CLI's `--help`, deployment target, and documentation matching the pinned versions before applying a workaround or current template. Record missing context as an `unverified gap`.

## Architecture Boundary

Choose Expo/React Native when cross-platform delivery and shared TypeScript domain/API/auth work dominate and maintained native modules cover the requirement. Choose native Swift/SwiftUI when an Apple-only surface, extension, deep framework, hardware integration, exact interaction, or native performance is central and long-lived. Choose a bounded hybrid slice when the product remains cross-platform but one capability has a clear native owner.

For a hybrid slice, define ownership, lifecycle, error semantics, version compatibility, data crossing the bridge, and proof surfaces before implementation. Agent familiarity or a single demo is not architectural evidence.

## Expo Change Matrix

| Change | Default class | Consequence |
| --- | --- | --- |
| JS/TS, styles, navigation, state/data flow | `js-only` | Reuse a compatible development binary and Metro |
| Native dependency/code, config plugin, scheme, entitlement, capability, SDK/runtime | `native-runtime` | Regenerate only as ownership permits; rebuild |
| Icon, splash, bundle metadata consumed by the native target | `native-runtime` | Rebuild the relevant artifact |
| Server/auth/backend contract | `shared-contract` | Prove mobile and server compatibility; broaden checks |
| OTA update | compatibility decision | Prove the target runtime accepts it; otherwise build a binary |

Expo Go is a sandbox for compatible JS-only prototypes. A development build is the normal local target for custom native modules, stable schemes, production-like OAuth callbacks, notifications, background work, and bundle-specific behavior.

## Native Ownership And Monorepos

Before prebuild, determine whether `ios/` is generated by Continuous Native Generation, manually owned, or mixed. Encode durable CNG changes in app config/config plugins. Preserve manually owned native projects; regeneration is a migration decision, not cleanup.

Use Bun first only when the lockfile/package metadata selects Bun. In Bun/Turborepo workspaces, inspect dependency resolution and verify single compatible React, React Native, and native-module versions. Modern Expo can configure monorepo Metro automatically; add resolver overrides only after reproducing a pinned-version resolution failure. After dependency or Metro changes, clear the relevant cache using the repo's existing command.

When mobile belongs to an existing product, preserve the intentional auth and backend boundary. Shared accounts/data usually mean the same auth project and backend deployment; a separate boundary requires an explicit product decision. Treat all client-bundled configuration, including public-prefixed environment variables, as readable. Server credentials stay server-side.

## Volatile Companion Routing

Use already-installed official Expo guidance for development clients, SDK behavior, build, and store detail; Clerk Expo guidance for installed auth APIs; Callstack guidance for measured performance work; and SwiftUI/native guidance only for Swift targets or native seams. Inspect their versions and sources. Keep their catalogs and fast-changing API recipes out of this skill.
